# 性能与成本优化

未加载时先读[共同规则](../../RULES.md)。保持当前主目标，不为加载专项方法重新分诊；执行 ACTION 后交付结果，不只汇报已读。专项技能从路由输出取实际路径。

## ACTION NOW

看目标负载与真实瓶颈，先消掉不必要的工作。

先减少不必要的工作，再考虑复杂加速机制。不要用更快完成少一半功能伪装收益。基准环境、工作量和语义必须可比；测试运行本身是反馈，不是另建一套基准平台的理由。

**交付：** 对明确负载有效的性能或成本改进，以及收益与代价的实际范围。

## ACTION

1. 选定用户关心的目标：延迟、吞吐、内存、启动、网络/磁盘量或费用。使用代表性数据和现有性能工具；若目标已给出就直接采用。
2. 观察目标路径，找支配成本的工作：重复计算、不必要 I/O、数据表示、算法规模、竞争或资源等待。证据指向哪里就改哪里，不先给出“加缓存、上并发”。
3. 优先消除不必要的工作。新增缓存要有权威来源、容量与失效责任；新增并发要有状态所有者、取消与资源上限；数据增长才是瓶颈时改变数据流或表示，而非只改局部语法。
4. 在同等语义、负载和可比环境下比较前后，并看相关代价。只在有噪声影响判断时增加重复测量；不先搭通用基准平台。
5. 保持结果、顺序、错误与副作用契约；允许的精度或功能变化必须明确。不能通过少做用户要求的工作伪装优化。

## DONE

改进作用于实际瓶颈，收益与代价可说明，相关行为正常。没有可运行环境时可以完成有依据的改进和测量入口，但不宣称未经测量的提速。未改善目标就修正或撤回自己的无益修改，不为保留复杂机制寻找理由。

线上已不可用且用户要恢复时走 operate，不先追求最佳性能。容量规划属于这里的分析任务，不自动授权新增付费资源。

**不要：** 用微基准结果承诺端到端收益；仅凭代码行数或异步语法判断速度；忽略尾部延迟、内存和取消成本。

依据：S7（SQLite 性能工程）、S5（重复计算与副作用）。
