# 专题 · 契约与兼容

这是主路线的补充，不另起项目。只处理本次触及的真实依赖或新建立的支持承诺。

## ACTION

先读或复用已加载的[共同规则](../../RULES.md)。定位本次真正受影响的消费者或数据，在正确边界保留行为或完成已批准迁移，然后回到原 PRIMARY；不先创建兼容清单或另开评审。

## 保什么，在哪里保

- 从实际调用、已保存数据、用户文档和既有支持约定确定边界：API/CLI、配置、格式、错误、顺序与副作用。对外可依赖行为不等于所有私有函数和偶然实现细节。
- 没有旧消费者就不建历史兼容。0.x 不是可随意破坏真实用户的许可；成熟仓库也不意味着隔离实验必须永久守旧。新接口需明确当前能力与限制，不自行承诺长期支持。
- 内部可以直接重组。需要保留旧输入/输出时，在清楚的边界转换为一个内部模型，尽量保持一个事实来源；不让每层猜版本，也不把无用包装当安全感。
- 契约需要改变且已获批准时，给用户可执行的迁移：谁受影响、旧写法如何换、数据含义如何保持、什么时候旧入口退出。安全修复按项目例外处理，不能为兼容保留漏洞。

## 数据和过渡

已有数据与混合版本可能共存时，按真实部署方式安排兼容读写和切换顺序。小型离线迁移无需默认双写；不能停写的在线迁移则必须明确真相来源、同步、失败处理和停止过渡条件。

代码回退、格式回退和数据恢复分别判断。不可逆转换有已授权的备份/恢复或可行前向修复；不把“可以重新部署旧代码”当成数据安全证明。

在受影响边界保留有代表性的旧调用或数据例子；不要为了兼容虚构全套版本矩阵。过渡完成后清理已无依赖的分支与说明；确属长期支持的契约按承诺保留，不强求所有适配器设倒计时。

完成的标志是用户继续可用或已获得批准的迁移路径，不是兼容层代码变多。
