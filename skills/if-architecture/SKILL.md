# 架构判断 · 决定复杂性在哪里结束

未加载时先读[共同规则](../../RULES.md)。这是当前 PRIMARY 的专项方法，不是另开一项架构工程。

## ACTION

1. 画清眼前的一条事实路径：谁产生数据，谁改变它，谁消费它，哪里发生外部效果。通常在工作记忆中即可，不强制产出图。
2. 找出必须一起成立的事实与修改责任。让不可能的状态难以表达；一个权威来源能覆盖的，不用几个布尔字段相互同步。已有缓存确有用途就保留并明确失效责任。
3. 按变化原因划界，而不是按“控制器/服务/管理器”模板分文件。接口承担完整操作，让调用者不必知道内部每个步骤。
4. 判断改动应该落在哪一层：生产、序列化、协调还是消费。别因症状出现在 UI 就在 UI 兜底；也别因能改基础层就扩大整个系统。
5. 选择当前整体最清楚的实现并完成它。优先显式主路径、领域名称和局部可理解，删除只转发却增加跳转的层；真正隔离资源和协议的适配器保留。
6. 改完调用和受影响的短地图，把“刻意不依赖什么、为什么这样划界”就地留下。不用长篇注释维护代码本可消除的耦合。

## DONE

目标功能或修复已经落到正确责任处，新会话能定位修改点，不必重新猜整套设计。结束专项工作，回原 PRIMARY 完成交付。

这里的判断规则是工程归纳。依据见[名仓库](../../references/source-lessons.md)和[痛点 P2](../../references/ai-coding-pain-points.md)。不把多层结构、依赖注入或所谓优雅本身当收益。
