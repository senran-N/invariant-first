# 设计与代码审查

未加载时读取 [共同判断](../../RULES.md)。交付有依据的发现，按证据更新结论；只读请求不授予修复权限。

## ACTION

1. 界定审查目标、基线与受支持条件，阅读差异、直接协作者、契约和关键测试。区分本次引入的问题、已有问题与方案假设；不要把全仓遗留问题归于本次变更。
2. 将可疑点还原为成立条件、实际或方案约定的路径、被破坏的保证及后果。核对上游校验、状态所有权和受支持配置；本机默认配置未触发，不代表其他受支持路径不成立。文档与代码冲突时，沿需求、消费者与设计依据判断该修哪一处。
3. 用可靠复现或可核查的推导检验关键因果关系，把结论限定在证据真正覆盖的条件。工具告警、他人意见与测试结果都须解释它们支持哪一步判断。重要疑问尚未证实时说明缺失的前提与后果，不写成确定缺陷；原因已清楚就不为形式重复验证。已有独立检查能力有助于关键判断时使用，不强制多 Agent。
4. 分别判断问题是否成立、建议修法是否保持契约。修正方向落到真正承担责任的位置；主观质量转成可观察标准，个人偏好不阻塞实质改进。接到其他审查意见时沿同样证据核实，不把评论当自动待办；用户授权修复才衔接 fix 或对应路线。
5. 按实际后果与紧迫性组织本轮已成立的发现，给出位置、触发条件、证据及修正方向。同一因果问题合并说明，不同问题不因表面相似合并；覆盖约定范围，不凑数量，也不按固定条数把已确认问题留到下一轮。未覆盖的重要边界单独说明。
6. 复核从原发现的成立条件出发，确认致错路径已消除，或用新证据撤回原判断；评论显示状态和本轮是否再次提及不作修复依据。只重查受变化影响的证据，保留仍成立的问题与有效工作，不为追求一次空报告无限重跑。

## DONE

范围内有依据的重要问题已交付，发现、待核实风险与非阻塞建议区分清楚。没有实质问题就说明范围内未发现；审查通过不是零缺陷证明。只读审查不改实现或测试；获准修复时验证真实保证，而不是只消除告警。
