# 设计与代码审查

未加载时先读[共同规则](../../RULES.md)。保持当前主目标，不为加载专项方法重新分诊；执行 ACTION 后交付结果，不只汇报已读。专项技能从路由输出取实际路径。

## ACTION NOW

对照目标读变更与直接协作者，找有具体后果的问题。

先理解作者要保持的行为和仓库惯例；无法指出可发生条件及后果的偏好，不报成缺陷。用户只要审查时不要改文件；要求审查并修复才衔接修复。检查代码与文档是否真的接入系统，而不是只检查片段看起来合理。

**交付：** 有具体依据、可行动的发现；没有实质问题就直接说明范围内未发现。不擅自把审查变成代码修改。

## ACTION

1. 对照本次目标阅读差异、直接调用者、涉及的契约和关键测试。审查方案时区分已实施事实与假设，不能拿假设当缺陷。
2. 先看功能是否成立、是否破坏真实用户、是否存在状态与权限错误；再看是否新增重复事实、隐含耦合、无依据防御或多余层次。
3. 每项发现给出具体位置、触发条件、结果及最直接的修正方向。没有可说明的后果，不包装成严重问题；个人风格偏好不阻挡实质改进。
4. 对触及的风险使用主入口的 contracts 或 state-and-boundaries，不附加一套通用安全/性能审计。需要检查来确认疑问就运行，不为了报告数量制造测试。
5. 主观质量先转成可观察标准再判断，例如信息层级、交互完成度、可读性或一致性；不要用“看起来不错”作为证据。宿主已经提供独立 reviewer/evaluator 且任务价值足够时可以利用，但普通修改不因此强制多 Agent。
6. 用户要求“审查并修复”时，确认问题后在授权范围内转 fix 或对应目标路线并完成；只要求 review 时保留为发现。不要为了自证审查有价值而造问题。

## DONE

重要问题已定位，依据和未覆盖范围清楚。代码整体变好且无实质阻塞时，不以追求完美拖延结果。审查通过不是零缺陷证明，未知不能写成确定错误。

**不要：** 列几十条一般最佳实践；借审查重写实现；用分数代替可行动发现；偷偷修改测试来让被审查方案成立。

依据：R4（Google 工程审查标准）、S6；只读与修复的授权区分是本 Skill 的操作规则。
