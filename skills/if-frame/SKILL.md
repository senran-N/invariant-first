# 定向、架构与接手

未加载时先读[共同规则](../../RULES.md)。保持当前主目标，不为加载专项方法重新分诊；执行 ACTION 后交付结果，不只汇报已读。专项技能从路由输出取实际路径。

## ACTION NOW

找真实入口与核心表示，做出一个能推进任务的取舍。

设计的结果必须能决定接下来的代码：数据表示、责任、主路径与一个明确取舍。陌生仓库先找到已有机制，不照搬自己熟悉的项目模板。用户已经要实现时，解决眼前设计问题后继续实现，不能把全项降格为方案。

**交付：** 一个选定的方向和可以行动的范围；接手时给真实代码地图。用户要方案就交方案，要实现就不要停在这里。

## ACTION

1. 从用户要解决的任务出发，写清谁用、输入什么、得到什么、本次不做什么。需求已明确就沿用，不重新访谈。
2. 新项目挑出最影响成败的一个技术未知，用最小技术实验消除它；普通可逆选择直接定。目标不清不能靠堆功能代替判断。
3. 已有项目从入口追到核心数据、状态修改者和直接调用者；用现有事实确认实现位置。接手不是全仓考古。
4. 选能让主路径最直接、后续修改最局部的方案，说明真正决定取舍的一两点。已有基础足够就用，不默认引入服务拆分、插件层或新依赖。
5. 确定模块承担的责任、核心数据及关键依赖方向。保留代码不易表达的选择理由和刻意排除的依赖；小项目写在已有 README 即可。

## DONE

读者能够开始实现或正确修改，设计任务即可交付。实施已在授权内就转 build；只要求设计或解释时不擅自改代码。若核心假设被事实否定，明确换方向及影响，不用演示数据粉饰可行性。

**不要：** 为每个选项写对称长篇论证；把立项模板、目录树或技术栈清单当作架构；因为新会话没历史就要求用户重述仓库已有事实。

依据：S1–S2 的小核心与数据表示、D4 的架构地图；选择单一方案和轻量接手是本 Skill 的操作归纳。
