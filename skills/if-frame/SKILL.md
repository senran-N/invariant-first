# 定向、架构与接手

未加载时读取 [共同判断](../../RULES.md)。先确定做对什么，再确定怎样做；设计要决定后续实现，不只给目录树或技术栈清单。

## ACTION

1. 从使用者要解决的问题辨认核心价值、已要求能力与成功标准。对有实质取舍的设计，简短复述重点，用一个具体场景核对理解；沿用已确认的信息，不默认替用户列“本次不做”。
2. 分清缺的是事实、偏好还是可行性证据。代码与环境事实先调查；会改变目标、能力含义或验收的意向分歧，按共同判断主动提问并给推荐。体验或可行性难以口头判断时，用样例、草图或授权内的小实验提供依据，不要求用户预先解决技术问题。回答到来后更新受影响的决定，不走形式。
3. 明确产生核心价值的机制：输入与可用信息如何影响判断、动作和结果，用什么证据区分好坏方案。优先研究这个关键未知，而不默认把稳定执行、接线或通用架构当成产品核心；必要基础可以先做，但不能替代主目标。足以决定的局部取舍直接作出，不为比较另造两套实现。
4. 已有项目从真实入口追到数据、责任与直接消费者，复用适用机制。选择满足目标且理解成本合理的表示与边界；保持真实契约，不照搬熟悉的分层、服务拆分或插件平台。
5. 让每项必需能力有对应责任、主路径与验证方式，尤其不能把最关键但最难的部分留成一个接口名。按价值、依赖与风险给出实施顺序；试验、首个增量与完整交付分开，范围或标准的改变按共同判断协商，不把后做偷换成不做。
6. 交付选定方向、关键取舍、验证依据和仍待决定的事项；说明它们怎样服务用户目标。新事实否定核心假设时及时说明影响与可行选项，不悄悄降级。必要理由放在已有责任位置，不另造模板档案。

## DONE

方案能指导核心能力的实现与验收，接手判断能指向真实修改位置；未决项与部分成果不冒充完整设计。只要求设计或解释时不擅自改代码；实施已在授权内就继续 build，不把设计阶段当作提前结束的理由。
