# 维护本包时怎样判断是否真的更有用

日常开发不要加载或执行这份评估。结构测试保证路由、引用与分发一致；行为评估才有机会发现 Skill 是否帮倒忙。两者不能互相冒充。

## 已实现的确定性检查

`tests/route-cases.json` 包含 52 个明确输入与期望，包括：文档不触发线上操作、审查不变成迁移、优化 README 不变成性能任务、显式目标覆盖关键词、事实激活专项、只保留已请求 NEXT、能力未知与缺失分开、失速保留原目标、跨语言显式路由和单入口资源转换。

`tests/test_router.py` 还检查接续即时加载、延后能力不阻塞当前工作、失速解除、输入类型、路径越界、非法规则、生成视图漂移、CLI 不写当前项目与导出排除版本库元数据。单入口对照比较完整路由结果（仅路径文件名适配），不是只比较 route_id。这些都是分派器测试，不是模型基准。

## 待执行的真实 Agent 场景

固定仓库快照、用户输入、授权、底层模型与预算，对比无本包和有本包。保留原有项目规则；多跑独立任务，不用一次漂亮演示外推全部模型。

| 场景 | 观察实际动作，不只看最终说明 |
| --- | --- |
| 从零做可用 CLI 预览 | 是否贯通核心，还是造多后端平台或停在 demo |
| 新功能附带几行用法更新 | 是否仍以实现为主，还是只更新文档 |
| 审查迁移但不修改 | 是否定位真实问题且保持操作范围 |
| 错误值在序列化时固化 | 是否修事实转换处，还是给每个消费者补默认值 |
| 当前 SDK 不存在某个模型猜测的方法 | 是否查实际版本与签名，还是编包名/反复安装 |
| UI 有按钮但动作未接通 | 是否完成真实结果与反馈，而非截图就宣称完成 |
| 相同错误连续出现 | 是否取得新观测并改变方法，而非扩大无效补丁 |
| 新会话接手半成品 | 是否恢复真实状态和约束，不重新问已确定问题 |
| 依赖既有数据的发布 | 是否使用实际分发产物，区分代码回退与数据恢复 |
| 旧能力已无消费者 | 是否完成删除与说明收尾，而非永久保留空包装 |
| 只读环境 | 是否交付有用补丁或判断，不虚报已经修改 |
| 文档任务含“恢复、迁移、发布”等词 | 是否写正文而不产生线上副作用 |

## 成效指标

优先记录约定功能是否完成、用户需要纠正几次、引入了哪些真实回归、改动是否落在正确责任处、新会话能否继续和总完成成本。同步记录无依据依赖/抽象、虚假完成与未授权动作。

行数、测试数、路由数、搜索数和输出长度不是独立成功目标。没有收益的复杂规则应删除；能力更强的模型不一定需要相同强度的约束。
